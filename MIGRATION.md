Version 0.2 changes the API and the SQLite schema because the old progress markers cannot authenticate filters or identify reorganizations.

1. Replace `CfHeadersBatch.headers` with typed `filter_hashes: Vec<bitcoin::bip158::FilterHash>`. Return the basic filter type (`0`), request start, stop hash, and `previous_filter_header` from the response. Checkpoints use `FilterHeader`, not `BlockHash`.
2. Implement `HeaderSource::tip() -> ChainTip` using a consistent height/hash snapshot, and `header_at_height() -> bitcoin::block::Header`. Supply genesis at height zero and validated headers with correct parent links. Header consensus validation remains the provider's responsibility.
3. Update custom stores to retain `FilterRecord` values from genesis, atomically append validated batches, and atomically rewind both commitments and scan progress. The last scanned height is now `Option<u32>`: `None` means unscanned, and `Some(0)` means genesis was scanned. Optional birth heights also preserve zero as a meaningful value.
4. Implement the required, durable `WalletHooks::on_rollback` callback. Remove wallet block effects above the retained height, including effects of match callbacks whose progress write failed. Both callbacks must tolerate replay without duplicate wallet effects. Keep watchlist derivations needed for rescanning.
5. Configure independent checkpoints or explicitly opt into a trusted filter source. `run_to_tip` now returns `SyncProgress`; checkpoint mode can stop before the current network tip. Do not mark the wallet fully synchronized when the returned authenticated tip is behind the network tip.
6. Use a **new SQLite database** when upgrading a wallet that has 0.1 progress. The constructor rejects legacy progress and leaves it intact. Back up the old database, reset the wallet's derived block state, and replay from the appropriate birth height with the new engine. Do not copy the old rolling hash or scan cursor into the new schema: they lack the commitments and block identities required for verification. Keep keys, descriptors, address derivations, and other wallet secrets in the wallet's own storage.
7. For newly imported scripts, use `rescan_from` to replay historical blocks. Watchlist updates made during a callback apply to subsequent blocks; the callback itself receives the entire matching block and should derive sufficient lookahead before returning.

SQLite remains bundled and always available. There is no `store-sqlite` feature. The optional `rpc` feature adds a Bitcoin Core transport. See the runnable `offline` and `bitcoin_core` examples for the complete current API.
